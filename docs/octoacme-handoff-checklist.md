# OctoAcme — Handoff Checklist

## Purpose
Use this checklist to make role expectations explicit before work moves between project phases or between delivery and support.

## How to use this checklist
- Copy the relevant section into the project issue, release plan, or meeting notes.
- Assign an owner to each unchecked item.
- Do not move work forward until blockers, approvals, and missing artifacts are visible.
- Link the completed checklist from the project board or release document.

## Initiation -> Planning
- [ ] Project Manager has scheduled kickoff and documented timeline assumptions.
- [ ] Product Manager has documented the problem statement, goals, and success metrics.
- [ ] Stakeholders / Sponsors for approvals and escalation are named.
- [ ] Engineering Manager has confirmed staffing or capacity assumptions.
- [ ] UX / UI and QA support needs are identified for the first milestone.
- [ ] Key risks, dependencies, and open decisions are captured in a shared location.

## Planning -> Execution
- [ ] Backlog items have owners, acceptance criteria, and estimates.
- [ ] Developers, QA, and UX agree that scope is clear enough to start.
- [ ] Security or compliance review needs are identified for sensitive work.
- [ ] DevOps / Platform dependencies are scheduled for environments, secrets handling, or deployment work.
- [ ] The RACI matrix has been reviewed for major decisions and sign-offs.
- [ ] Stakeholder communication cadence is documented.

## Execution -> Release
- [ ] Acceptance criteria are met and linked from the release candidate.
- [ ] QA has recorded test coverage, defects, and go/no-go notes.
- [ ] DevOps / Platform has confirmed deployment steps, rollback plan, and monitoring.
- [ ] Product Manager has approved launch scope and release messaging.
- [ ] Customer Support / Success has launch notes or customer communication prepared.
- [ ] Open risks and contingency owners are documented before deployment.

## Release -> Support
- [ ] Post-release verification owner is named.
- [ ] Support team has known issues, escalation paths, and customer-facing guidance.
- [ ] Metrics, dashboards, or alerts for the release are being monitored.
- [ ] Incident communication owner is named in case of customer impact.
- [ ] Follow-up fixes or watch items are logged with owners and due dates.

## Sprint / Milestone Close -> Retrospective
- [ ] Project Manager has captured delivery outcomes, blockers, and timeline variance.
- [ ] Product Manager has captured metric signals, customer feedback, and missed assumptions.
- [ ] Engineering Manager, Developers, QA, and DevOps have identified operational or technical pain points.
- [ ] Action items have owners and target dates.
- [ ] Stakeholders know which follow-up decisions or investments are still required.
